**最需要关注的三个问题（均已修复）：**

1. **可以绕过登录调用全部后台接口**：把地址中的字母改写成 `%xx` 编码（例如 `/%61pi/outputs`），就能不登录读取特效页密钥、导出配置、解绑 B 站账号、上传文件。已在线上复现并修复。查阅了服务启动以来的全部请求日志，没有发现外部利用的记录。
2. **一个损坏的数据包就能让服务崩溃**：B 站推送的压缩数据损坏时，解压抛出的异常没有被接住，进程直接退出。
3. **一种畸形数据包能让服务卡死**：包长度为 0 时拆包循环原地打转，整个服务停止响应。由于进程没有退出，systemd 不会自动重启。

**说明：** 服务一直以 root 身份运行，而服务器上还跑着其他服务。这不属于代码缺陷，但会放大任何漏洞的后果，审计中一并处理，改为以低权限专用账号运行（见 5.3 节）。

## 2. 审计方法

1. **分方向并行审查**：按上表 6 个方向各自独立审查，全程只读，不改代码，不影响线上服务。
2. **逐条核实**：每个发现都重新阅读对应代码确认，排除误报。关键问题实际复现过：
   - 登录绕过：在线上服务上用编码地址请求，返回 200（修复后为 401）。
   - 崩溃和卡死：用脚本构造损坏的压缩包和长度为 0 的包，分别验证进程退出和死循环。
   - 事件记录翻页：在内存数据库放入 30 万行，确认查询计划需要临时排序，每页约 180 毫秒。
   - 上舰重复播放：用脚本模拟 GUARD_BUY 先到、toast 晚到 3 秒以上，确认输出两次。
3. **按方向分批修复**：每批一个分支，补充能复现问题的测试。关键测试会先在未修复的代码上确认失败，修复后确认通过。每批通过完整检查（`pnpm check`：类型检查、代码检查、全部测试）后合并到 `dev` 并上线。
4. **上线后验证**：接口健康检查、特效页连接、登录、备份写入；管理后台所有页面在浏览器中逐页打开，确认没有脚本错误。

## 3. 审计前的相关修复：特效页假死

审计开始前，排查并修复了"特效页在直播软件里假死、不再显示特效"的问题（`e040540`、`322abea`）：

- **原因**：直播电脑经代理访问服务，代理切换线路时会悄悄丢掉连接，浏览器收不到关闭事件；特效页没有自己检查连接是否还活着，于是一直以为在线、不再重连。
- **处理**：
  - 服务端每 15 秒发一次心跳，特效页 45 秒收不到任何消息就主动重连。
  - 特效页每 20 秒报一次平安，服务端 90 秒收不到就判定页面卡死并断开。
  - 服务端日志记录每次连接、断开及原因，以及每个特效是否真的开始播放。
- **验证**：15 分钟连续播放压力测试，内存与页面元素没有增长；线上实测浏览器后台标签页被冻结后，服务端按预期判定卡死并断开。

## 5. 服务端安全

合并提交：`15ab9c6`（登录绕过，单独紧急修复）、`c8085a9`、`00472f9`

### 5.1 登录绕过（严重）

| 项目 | 内容 |
|---|---|
| 编号 | S-1 |
| 位置 | `apps/server/src/app.ts` 登录检查钩子 |
| 原因 | 登录检查用原始地址判断 `req.url.startsWith('/api/')`，而 Fastify 在匹配路由前会先解码 `%xx`。`/%61pi/outputs` 不以 `/api/` 开头，跳过了检查，却匹配到了 `/api/outputs` 路由 |
| 影响 | 公网上任何人都可以：读取特效页密钥并向直播画面推内容；导出、导入配置；上传文件；解绑或换绑 B 站账号 |
| 处理 | 改用路由匹配到的路径模板判断，并用解码后的地址兜底；地址编码不合法时返回 400 |
| 验证 | 新增测试覆盖多种编码写法；线上验证编码地址返回 401；日志中没有外部利用记录 |

### 5.2 其他安全问题

| 编号 | 级别 | 问题 | 处理 |
|---|---|---|---|
| S-2 | 中 | 上传约 1 MB 的 SVGA 压缩炸弹，解压后可达数 GB，超出内存上限被系统杀掉；Lottie 文件最大可达 100 MB，直接整个解析 | ✅ SVGA 解压上限 64 MB；Lottie 文件上限 20 MB |
| S-3 | 中 | 服务以 root 运行，没有任何沙箱 | ✅ 见 5.3 节 |
| S-4 | 低 | ffprobe 按内容猜测格式：在 `.mp3` 里放入播放列表，可以让它去读本机其他文件 | ✅ 按扩展名指定格式，只允许读本地文件 |
| S-5 | 低 | 放在反向代理后面时，所有请求都显示来自 127.0.0.1，登录限流变成全站共用；Cookie 永远不带 secure；改密码后下发的 Cookie 没有判断 HTTPS | ✅ 新增 `STARFALL_TRUST_PROXY` 设置；两处 Cookie 都按 HTTPS 加 secure |
| S-6 | 低 | 退出登录只清除浏览器里的 Cookie，被盗的 Cookie 在 30 天内仍然有效 | ✅ 会话带编号，退出时加入注销名单（到期自动清理） |
| S-7 | 低 | 初始密码明文写进系统日志 | ✅ 日志只写密码文件的位置 |

**检查过、没有问题的方面：** 密码用 scrypt 加随机盐存储，比较为恒定时间；Cookie 为 HttpOnly、SameSite=Strict；特效页密钥为 128 位随机数、恒定时间比较，日志中已隐去；管理后台实时连接检查来源和登录；静态文件没有路径穿越；上传有扩展名白名单和文件头检查，不接受 SVG、HTML；导入配置包没有路径穿越（zip slip），有大小限制和严格校验；登录信息用 AES-256-GCM 加密；错误响应不带调用栈；没有发现会导致正则回溯卡死（ReDoS）的正则，也没有能让服务端代为请求任意地址的接口。

### 5.3 运行权限调整

- 新建系统账号 `starfall`，服务以该账号运行，数据目录归它所有。
- systemd 沙箱：只能写数据目录（`ProtectSystem=strict` + `ReadWritePaths`），禁止提权、隔离 `/home` 和 `/tmp`、不能访问设备、不能加载内核模块、只能使用网络和本地套接字。
- 注意：启动时需要读取网卡列表，必须放行 `AF_NETLINK`（第一次上线时因此启动失败，已修正）。

## 10. 部署与运维变化

1. **运行账号**：服务改为以 `starfall` 账号运行，数据目录 `/opt/starfall/data` 归它所有。重置后台密码的命令改为：
   ```bash
   cd /opt/starfall && runuser -u starfall -- node apps/server/src/cli/reset-password.ts
   ```
   用 root 直接运行可能让数据库的临时文件变成 root 所有，服务随后无法写入；万一发生，执行 `chown -R starfall:starfall /opt/starfall/data`。
2. **新设置** `STARFALL_TRUST_PROXY`：放在 HTTPS 反向代理后面时填代理地址（同一台机器填 `127.0.0.1`）。部署指南已补充，Nginx 示例加上了 `X-Forwarded-Proto`。
3. **数据库升级** `0003_events_page_index`：新增两个事件索引，启动时自动执行。
4. **备份文件名**：手动备份形如 `starfall-20260926-153012-m.db`，与自动备份分开保留。
5. **登录**：会话格式变化，上线后所有设备需要重新登录一次。
6. **特效页**：已经打开的特效页要在直播软件里刷新一次，才能用上新的连接保活和特效页修复。
7. **新日志**：特效页的连接与断开（含原因、时长）、每个特效是否真的开始播放、B 站协议层的警告（每分钟合并一条）。

## 11. 后续建议

1. **发布 v1.0.1**：这批修复包含一个严重安全问题，建议把 `dev` 合并到 `main` 并打标签，作为稳定版本。
2. **公网访问改走 HTTPS**：按部署指南配置反向代理，设置 `STARFALL_TRUST_PROXY`，并关闭 17520 端口的公网访问。目前后台密码和 Cookie 仍以明文经过网络。
3. **开源前清理提交历史**：旧的提交记录和分支里仍有服务器地址、主播 UID 等信息（当前代码里已经没有）。
4. **B 站登录自动续期**：实现刷新令牌流程，避免直播中途登录失效。
5. **定期复查**：B 站协议随时可能变化，建议每次大版本前复查协议解析，关注新日志里的协议警告。
